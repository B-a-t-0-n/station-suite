# Обычный Wi-Fi с запретом известных адресов Яндекса

Выбранный пользователем режим: обычный доступ Станции в интернет без
внешнего VPN, с запретом известных IPv4-направлений штатной Алисы и без
гарантии предотвращения обновлений. Это отдельный компромиссный режим,
отличающийся по политике от закрытого выхода с точечными разрешениями.
18 ноября 2026 года этот режим проверен на нашей Станции Макс, включая
перезагрузку с отключённым Ethernet-кабелем и остановленным транспортом ПК.
Пользователь подтвердил ответ новым голосом и включение музыки после загрузки.
[Результаты проверки](results/ordinary-wifi-known-deny-2026-11-18.json).

Применены и повторно прочитаны после загрузки 14 адресных запретов.
Три выбранных адреса недоступны со Станции и доступны из другого источника;
обычный HTTPS по Wi-Fi проходит с проверкой сертификата. Отдельное Android-
приложение получило HTTP 200 через сеть по умолчанию, без явной привязки сокета.
Это проверка обычного доступа приложений, а не проверка каждого ТВ-сервиса.
[Исходник адресного пробника](../../experimental/wifi-standalone/tests/device/KnownAddressProbe.java)
публикуется отдельно: он выбирает Wi-Fi явно, проверяет исходный адрес и
делает один TCP connect к публичному IPv4:443 без передачи данных.

Локальные DNS, HTTP204 и TLS config с `hasUpdate:false` подтверждены под UID
Quasar. Синтетический запрос через внешние голосовые API напрямую по Wi-Fi
занял 3027 мс; он не использовал микрофон и не воспроизводил звук.
После reboot самостоятельно запустились Agent, локальные службы, голос и
обычный split VPN. Зафиксированы свежий системный NTP-ответ и правильное
время; native голосовой канал подключился к локальному обработчику.

ПК использовался для настройки и наблюдения по ADB. Голосовые запросы,
музыка и интернет Станции через него не проходили. Телефонная навигация
использует Bluetooth HID; после долгой перезагрузки может потребоваться
переоткрыть пульт. Автозапуск shell-процесса для стрелок веб-панели не доказан.

На домашнем RV6699 правила IP Filtering ограничиваются одним подготовленным
IPv4-адресом Станции с маской `/32`. Для каждого известного адреса назначения
создаётся запрет `/32` на все порты TCP и UDP. Остальной трафик следует
обычной политике роутера. Правила не различают UID или приложения: ТВ может
потерять доступ к ресурсам, использующим тот же запрещённый IP.
Глобальная фильтрация доменов, настройки остальных устройств и IPv6
домашней LAN этой схемой не меняются.

Локальный split VPN Suite нужен только для доставки config/push/DNS в наши
службы на Станции. Он не является внешним туннелем для интернета и не
считается системным запретом OTA: уже установлен
[обход VPN привилегированным Quasar](vpn-system-bypass.md). Ограничение
известных внешних адресов действует отдельно на роутере.

[Инвентарь имён](../../config/known-yandex-native-hosts.json) основан на
сохранённом `quasar-prod.cfg` сборки `20221212`; SHA-256 указан в JSON.
Он охватывает config, голос, push, авторизацию, музыку, IoT, геолокацию,
проверку связи и телеметрию. Имя `station-config.quasar.yandex.net`
добавлено нашей реализацией локального push. Общие адреса статических
ресурсов не входят в минимальный набор. Публичный JSON содержит только
имена, роли и выбор набора; актуальные DNS-ответы и привязка Станции
остаются в частной конфигурации.

Подготовленная последовательность перехода сохраняет закрытый выход,
пока новые запреты не проверены:

1. Сохранить точные исходные группы и правила, проверить привязку Станции
   и запустить независимый возврат к закрытой политике.
2. Добавить адресные запреты за существующим общим запретом; выполнить
   Apply и прочитать каждое правило обратно.
3. Удалить только общий запрет Станции, выполнить Apply и проверить
   обычный HTTPS, известные запрещённые направления и локальные службы.
4. Подтвердить режим после проверки. При ошибке сначала восстановить и
   применить общий запрет, затем убрать только добавленные правила.

DNS-адреса меняются и могут использоваться несколькими сервисами.
Полного списка серверов загрузки OTA в исследованной конфигурации нет.
Другие адреса, протоколы и IPv6 этим IPv4-набором не покрываются;
сохранённые или новые направления обновлений могут остаться доступны.
Работа ТВ и отрицательные проверки известных адресов поэтому не доказывают
защиту от обновления после перезапуска.

Смежные исследования: [возможности RV6699](router-rv6699.md),
[разделение ТВ и штатных служб](selective-tv-egress.md).

## Сохранённая конфигурация

В Voicebridge выставлены числовое `lab_proxy_port: 0` и музыкальный
`transport: "direct"`; остальные приватные поля сохранены. Обычный
WifiRelayService запущен с `durationMs=0`, его preference включает старт
после BOOT_COMPLETED. Сохранённая Wi-Fi-сеть использует подготовленный
статический адрес, совпадающий с source `/32` правил и резервацией роутера.
Системные `auto_time=1`, `ntp_server=194.190.168.1` проверены после reboot.

Постоянный частный `state/stop` не даёт проводному PC owner снова выключить
Wi-Fi. Возврат к нему требует сначала закрыть выход на роутере, отключить
Wi-Fi-профиль при включённом радио, остановить split VPN и вернуть исходные
два поля из точной приватной резервной копии. Только затем снимается свой
stop-marker и запускается проводной runtime. Старый зелёный OTA-guard
для изолированного Ethernet к этому режиму не относится.

Этот проход проверил программную перезагрузку. Отключение питания и
перезагрузка роутера не проверялись; безусловная блокировка OTA не заявляется.
