# SystemControl и яркость кольца Макс

Проверено 16 ноября 2026 года на `yandexstation_2`, Android 9,
`PPR1.180610.011.20221212`. Это результат для конкретной прошивки.

## Подтверждённый канал чтения

Обычное чтение `/sys/class/backlight/fb5/brightness` из shell и доступных
app UID запрещено. Однако штатная служба Amlogic SystemControl имеет
нужный доступ. Политика разрешает `priv_app` находить
`systemcontrol_hwservice` и вызывать `system_control` через Binder.

Одноразовый Java-процесс, запущенный через имеющийся отладочный
`run-as ru.yandex.quasar.app`, успешно вызвал:

```java
vendor.amlogic.hardware.systemcontrol.V1_1.ISystemControl.getService(false)
// inherited from V1_0:
readSysfs(String path, ISystemControl.readSysfsCallback callback)
```

Получены реальные значения:

```text
/sys/class/backlight/fb5/brightness     255
/sys/class/backlight/fb5/max_brightness 255
/sys/class/graphics/fb5/name           YNDX LED ring
```

Это не требует установки `su`, смены SELinux, прав framebuffer, прошивки
или остановки native Quasar. Обычный APK пульта/Agent от этого не получает
привилегии. Доступ к приложению Quasar через ADB и пригодный `run-as`
являются предпосылками текущего эксперимента.

## Почему одного результата API недостаточно

В исследованном native backend `readSysfs` и строковый `writeSysfs`
могут сообщать успех независимо от результата файловой операции.
Нужны проверка содержимого и отдельный readback после записи.
У HIDL backend не найден список разрешённых путей; наш эксперимент
фиксирует только яркость fb5, диапазон и точное имя устройства.

В Java API есть также `writeSysfsBin(String, int[4096], int)`. Это общий
файловый writer, не готовый контракт анимаций. Его наличие не доказывает
доступ к framebuffer или правильную синхронизацию кадров. Статический
разбор указывает на возможную утечку 4096 байт на вызов в этой версии.
Этот метод не вызывался и в эксперимент не включён.

Позднейший [разбор RGB-транспорта](ring-rgb.md) подтвердил утечку на
проверенном пути образа и уточнил, что точный драйвер синхронизирует кадр
при закрытии fd. Это не подтвердило разрешение SystemControl на framebuffer
и не превратило метод в пригодный постоянный renderer.

## Короткая проверка яркости

Исходники и тесты: [experimental/ring-dimmer](../../experimental/ring-dimmer/).
Эксперимент уменьшает исходную яркость до 75%, затем восстанавливает её.
Он не выбирает RGB-цвет, не включает погашенное кольцо и не записывает
кадры поверх native-процесса.

На устройстве финальный запуск завершился с кодом 0 и вывел `DIMMED`,
`RESTORED`. Отдельные чтения подтвердили `255 → 191 → 255`, затем три
отложенные проверки снова вернули `255`. Это подтверждение системного
значения; визуальная оценка изменения пользователем отдельно не получена.

В этом UID запрещено чтение `/proc/uptime`. Watchdog использует
`System.nanoTime()` Android через узкую команду `ticks`, без HIDL-запросов.
Clock-клиент имеет отдельный таймаут; общий deadline HIDL-теста — 6 секунд.
Это ограничение запуска восстановления, не жёсткая гарантия времени
физического возврата яркости.

Драйвер применяет множитель при следующем штатном `fb_sync`. Поэтому
в полностью неподвижном состоянии визуальное изменение может быть
не видно до следующего кадра. Глобальная яркость затрагивает также
системную индикацию микрофонов, таймеров и ошибок.

Отдельный watchdog прекращает тестовый клиент и пытается вернуть
сохранённую яркость. Сервер HIDL использует до 16 потоков: убийство
клиента не отменяет уже принятый сервером запрос. При зависании сервера
или ядра жёсткой гарантии возврата нет. Это диагностический эксперимент,
а не готовый постоянный сервис подсветки.
