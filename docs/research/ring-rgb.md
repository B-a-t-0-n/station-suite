# RGB-кольцо: следующий этап после спектра

Проверка 16 ноября 2026 года: Станция Макс `yandexstation_2`, Android 9,
прошивка `20221212`, ядро `4.9.113`. [Спектр штатной музыки](music-spectrum.md)
уже подтверждён отдельным APK. Этот этап проверяет доставку RGB-кадров и
сохранение штатной индикации. Постоянный RGB-writer не устанавливался.

## Что удалось уточнить

| Часть | Результат |
| --- | --- |
| Аппаратные каналы | В живом device tree найдены 24 RGB-светодиода, два контроллера `is31f3236a`; первый red label — `station2:red:ring1`, trigger — `led_ring_fb` |
| Общая яркость | HIDL-чтение по-прежнему возвращает `255/255`; ранее проверенный диммер остаётся отдельной возможностью |
| Отдельные RGB-каналы | Точечное HIDL-чтение ожидаемых brightness/max_brightness/trigger вернуло пустые строки; доступ не подтверждён |
| Кадр framebuffer | В точном модуле драйвера `fb_release` вызывает `fb_sync`: запись и закрытие fd потенциально синхронизируют кадр без отдельного ioctl |
| Доступ посредника | В четырёх доступных CIL-частях не найдено разрешение `system_control` на `graphics_device:chr_file` или `sysfs_leds:file` |
| Постоянный binary writer | В исследованном образе обнаружена утечка 4096 байт на вызов; для светомузыки не применяется |
| Состояние native | Пассивное подключение к локальному IPC дало состояние Алисы, таймеров и конфигурации; полнота набора защитных состояний ещё не подтверждена |

При аппаратной проверке не менялись цвета, LED-trigger, общая яркость,
права устройств, SELinux, прошивка или native-процессы. Одноразовый helper
чтения метаданных после проверки удалён. Данные аккаунта и сырые IPC-пакеты
не публикуются.

## Почему нельзя использовать найденный SystemControl как готовый renderer

Установленный Java API содержит `writeSysfsBin(String, int[4096], int)`.
В исследованном `systemcontrol` HIDL wrapper выделяет 4096 байт и не
освобождает этот буфер на проверенном пути. При 10 кадрах в секунду это
около 141 MiB в час в долгоживущей системной службе. Ветка неполной записи
также не закрывает уже открытый fd. Возвращаемый успех не гарантирует запись.
Это статический результат для fingerprint образа, а не эксперимент с
накоплением памяти на живой колонке.

Строковый writer использует `strlen`, поэтому не является транспортом
произвольных RGB-байтов с нулевыми компонентами. Ограниченные ASCII-кадры
не решают ни восстановление, ни доступ к framebuffer, ни владение им.

У точного `quasar_led_ring.ko` callback `fb_write` отсутствует, а `fb_release`
вызывает `fb_sync`. Поэтому прежнее предположение «обязательно нужен отдельный
ioctl» слишком сильное: open/write/close теоретически достаточно при разрешённом
доступе и совместимом vendor core. Это **не проверенный живой RGB-канал**.
Upstream [fb_write Linux 4.9.113](https://github.com/gregkh/linux/blob/v4.9.113/drivers/video/fbdev/core/fbmem.c#L763-L830)
синхронизирует старый буфер до копирования; отдельный
[fb_release](https://github.com/gregkh/linux/blob/v4.9.113/drivers/video/fbdev/core/fbmem.c#L1400-L1412)
вызывает callback драйвера при закрытии descriptor.

Root UID системного сервиса не отменяет SELinux. Успешное чтение backlight
не доказывает доступ к другому inode с типом `graphics_device`. Проверены
живые `vendor_sepolicy.cil`, `plat_pub_versioned.cil`, `plat_sepolicy.cil` и
`mapping/28.0.cil`, включая source attributes. Полный compiled policy прочитать
не удалось; вывод ограничен перечисленными частями и фактическими чтениями.

## Штатная индикация и возврат управления

Прослушивание, ответ, отключённые микрофоны, таймеры и ошибки должны вытеснять
музыкальную анимацию. Пассивный IPC-клиент не равен контракту владения: даже
правильно распознанное состояние не даёт атомарно перехватить и вернуть
framebuffer. Восстановление старого или чёрного кадра тоже не означает
восстановление актуальной штатной анимации.

Отдельная трёхсекундная пассивная проба получила `DeviceState` с явным
`alice=IDLE`, `alarm_playing=false`, `timer_playing=false`, `configuration=CONFIGURED`.
Поле микрофонов в этом сообщении отсутствовало. Оно не интерпретируется как
«микрофоны включены». Проба отправила **0 байт** в native IPC; временный ADB
forward снят. Полные сообщения в файлы не сохранялись.

Реализация наблюдателя находится в
[`experimental/ring-state`](../../experimental/ring-state/). В отдельной
проверке этого кода за три секунды получено 83 IPC-кадра, из них один
`DeviceState`: состояния микрофонов, обновления и звонка остались неизвестными.
Открытое соединение не подтверждает свежесть: последнему снимку при завершении
уже было около трёх секунд, native timestamp отсутствует. Наблюдатель всегда
возвращает `renderPermit=false`. Проверены 19 тестов границ, wire-format,
presence и пассивного приёма; пройдено независимое ревью.
[Обезличенный результат](../../experimental/ring-state/results/native-20221212.json).

Для постоянного режима остаются два конкретных условия: узкий привилегированный
исполнитель кадров без утечки и доказанный договор со штатным LED-владельцем.
Пока они не выполнены, приложение не показывает RGB-эффект как применённый.
Текущий ADB shell имеет UID 2000; устройство сообщает `ro.debuggable=0`,
`ro.secure=1`, build type `user`, tags `release-keys`. Добавление нужного
исполнителя требует отдельной работы с привилегированным слоем устройства,
а не только установки ещё одного обычного APK.
