# Автономный Wi-Fi на Макс: состояние исследования

Проверки 16–17 ноября 2026 года, Android 9, `PPR1.180610.011.20221212`.
Цель — домашний Wi-Fi без ПК и дополнительного роутера: служебные запросы
Станции остаются локальными, наружу разрешены только нужные API и медиа.
**Готового режима безопасного автономного Wi-Fi пока нет.**

17 ноября [проверка домашнего RV6699](router-rv6699.md) подтвердила
исходящие IPv4 TCP/UDP правила и порядок Allow перед Deny в двух группах.
Отдельная согласованная проба на телефоне подтвердила разрешение одного
адреса перед wildcard destination deny при всех исходных портах; откат
восстановил доступ. Единственный текущий WAN HSI настроен как IPv4-only,
при этом IPv6 в домашней LAN оставлен включённым. Это снимок конфигурации,
а не гарантия будущего отсутствия внешнего IPv6. На Станции
также проверено управление IPv6 только `wlan0` без root при выключенном
Wi-Fi. Применение до первого подключения и сохранение после reconnect/boot
не доказаны. Аудит точных live framework-файлов не нашёл сохраняемого
IPv6-disable параметра обычной Wi-Fi-сети; временный setter не закрывает
эту задачу. Поэтому это ещё не готовая политика автономного Wi-Fi.

Следующая короткая проба выполнена уже на Станции: до подключения
применены правила для её закреплённого IPv4 — LAN разрешена, внешний
TCP/UDP запрещён. Станция вошла в Wi-Fi, телефон открыл Agent по этой
сети с HTTP 200. Проверочные внешние HTTPS и UDP DNS не прошли.
Нужные API и медиа наружу пока не разрешались. После пробы Wi-Fi
выключен, профиль отключён, проводные службы и панель восстановлены;
две группы и резервация на роутере оставлены. Это проверка сетевого
механизма, а не автономной работы или защиты native OTA при загрузке.
[Подробности и границы](router-rv6699.md#станция-за-предварительно-установленным-запретом).

Последующая подготовка разрешений для 38 внешних имён дала 47 точных
IPv4/порт правил, но прервалась до включения Wi-Fi; голосовые API и музыка
через них ещё не проверены. Временные allow отдельно удалены, закрытая
политика прочитана и применена повторно. После этого Windows показала
отключённый Ethernet Станции, проводной runtime — ошибку guard. Для
продолжения нужна физическая связь; прежний `ready` относится к прошлому
проходу. [Результаты и исправления контроллера](router-rv6699.md#подготовка-разрешений-внешних-сервисов).

После отдельного согласования прямого интернета без гарантии OTA установлен
[экспериментальный Wi-Fi-модуль](../../experimental/wifi-standalone/README.md).
В сеансе до перезагрузки Ethernet был физически отключён, транспорт ПК остановлен.
Через домашний Wi-Fi подтверждены Agent HTTP200, HTTP204 и локальный TLS config
под UID Quasar с `hasUpdate:false`, а также свежий поиск музыки через direct HTTPS.
Пользователь подтвердил голосовой ответ и воспроизведение песни без кабеля.
После перезагрузки пользователь сообщил, что Станция завершила обновление.
Это сообщение сохранено как `user_reported`, а не подтверждение установки новой ОС.
После factory reset, официальной проводной настройки и одной перезагрузки
ADB восстановлен. Прочитаны прежние Android 9/build `20221212`/fingerprint,
native версия `1.56.1.34.1553780878.20221212.22` и системный Quasar APK `2.0`/code2.
SHA256 живого `/system/vendor/quasar/maind` —
`08a0050f4ad26e1054321c46d2e3631a6b02805e5e0355c10cbcbf53ea82ea6d` —
совпал с сохранённым до сброса. Установка новой ОС/native-прошивки не подтверждена.
Возможные обновления APK до factory reset теперь не установить; утверждать,
что обновлений вообще не было, нельзя. **Безопасность VPN от OTA не доказана.**
Suite APK были удалены сбросом. Затем восстановлены приложения, модель,
приватные настройки, локальные службы, лаунчер и Bluetooth-сопряжение;
пользователь подтвердил ответ новым голосом. Текущее состояние:
Wi-Fi выключен, изолированный Ethernet, SELinux Enforcing, shell UID2000.
Подготовлен [сценарий восстановления](../RECOVERY.md). Повторный холодный
запуск TCP ADB ещё не подтверждён; он не следует из наличия boot receiver.
[Отчёт](../../experimental/wifi-standalone/results/device-session-20221212.json)
сохраняет прежние проверки отдельно от сообщения пользователя и последующего
чтения версий/хеша после восстановления ADB.

В коде модуль запускается после `BOOT_COMPLETED`, при сохранённом preference
и действующем разрешении VPN; перехват создаётся позднее, после подготовки
worker. Защиты до запуска приложения нет; default route и IPv6 не перехватываются.
Ранее подтверждён и системный обход VPN. Это потенциальные пути обновления,
но журнал конкретного OTA не получен; сообщение пользователя не устанавливает
тип обновления или причину потери доступа.
Автономный запуск всех компонентов после boot не подтверждён; shell input
helper в прежней конфигурации требовал ADB bootstrap.

Модуль доставлял известные служебные запросы локально, но не является общим
интернет-фильтром. Приведённые ниже изолированные VPN-тесты сохраняются как
история исследования; прежний рабочий сеанс не отменяет системный обход VPN.

Следующая [проверка native OTA control](native-ota-control.md) установила
отсутствие доступных прав на изменение installer/launch и не нашла live
команды остановки updater у supervisor. Там же уточнена старая история
локальных root-попыток: её нельзя считать готовым безопасным автозапуском.

## Проверка домашнего роутера

17 ноября получен доступ к RV6699 с текущей прошивкой `v4.4.59`.
Временные black-list и IP Filtering правила сохранялись в панели; новые
соединения тестового телефона через Wi-Fi продолжали проходить. При
последующей проверке штатного JavaScript обнаружен пропущенный отдельный
шаг глобального Apply. Поэтому прежние пробы не устанавливают работу
фильтра после применения. Повторный тест с Apply подтвердил исходящий
IP Filtering на HSI в режиме Medium: два новых TCP/443 соединения к
запрещённому адресу не установились, контрольный адрес отвечал. Удаление
правила с повторным Apply восстановило доступ.
Во время этих первых проб Станция к домашнему Wi-Fi не подключалась.
После них восстановлена исходная резервная копия роутера; параметры
firewall, пустые таблицы фильтров и доступ в интернет проверены повторно.
Механизм IPv4/TCP фильтрации подтверждён; политика защиты самой Станции
от OTA пока не проверена. Позднее добавлены резервация и две группы
Станции, описанные выше; поэтому пустые таблицы относятся к раннему
восстановлению, а не к текущему состоянию роутера. Вывод о неисправности
фильтров на основании прежних проб был преждевременным.
[Условия и результаты проверки](router-rv6699.md).

## Найден обход VPN при выборе физической сети

Следующий десятисекундный тест подтвердил: тестовый процесс под UID Quasar
может выбрать Ethernet через `Network.bindSocket` и получить HTTP204 вне TUN,
пока VPN работает. Обычный запрос и запрос с заданным IP-источником до и после
этого прошли через TUN. UID Quasar входил в диапазон secure-VPN rules;
журнал заголовков полный, все четыре проверки завершились до дедлайна.

Quasar здесь — предустановленный `SYSTEM`/`PRIVILEGED` пакет, хотя его UID
больше 10000. Это не проверка обычного стороннего приложения. Прямой
`SO_BINDTODEVICE` под тем же UID получил `EPERM` до соединения; такой отказ
не отменяет успешный обход другим API. Все запросы шли на изолированный
лабораторный сервер, настоящий интернет и домашний Wi-Fi не подключались.

[Исходники и подробности](../../experimental/vpn-relay/SOCKET-ROUTE-CANARY.md) ·
[Сокращённый отчёт](../../experimental/vpn-relay/results/socket-route-device-20221212.json) ·
[Почему always-on/Device Owner не устраняет системные исключения](vpn-system-bypass.md).
Этот результат означает, что готовая пересылка трафика внутри VPN ещё не
является запретом прямого выхода. Использует ли этот обход сам updatesd,
по-прежнему не установлено. Режим lockdown в данном тесте не включался.

## Рабочая локальная доставка

На самой Станции проверен путь:

```text
TUN → Java packet policy → hev/lwIP → SOCKS loopback
                                      ├─ local config TLS
                                      ├─ local push TLS
                                      └─ local HTTP connectivity stub
```

Это отдельный [лабораторный APK](../../experimental/vpn-relay/README.md),
не включённый в основные приложения или автозапуск. Он на 10 секунд
перехватывает один частный IPv4 `/32` в изолированной проводной сети;
Wi-Fi выключен. DNS, default routes, always-on и lockdown не меняются.
ADB UID2000, Agent и Voicebridge исключены. Независимый shell-watchdog
проходит challenge/HMAC и завершает только тестовый пакет через 15 секунд
после аутентификации; без ARM максимальный срок — 30 секунд.

Перед VPN отдельно проверены загрузка библиотеки и её JNI-контракт в
одноразовом процессе: синтетические echo reply и TCP SYNACK, затем native
stop/join. [Результаты без VPN](../../experimental/native-tun2socks/runtime-smoke/results/device-20221212.json).
Пакетный движок собран из закреплённых исходников под API28/ARM64;
случайный готовый AAR не используется.

| Проверка последнего прохода | Результат |
| --- | --- |
| Контрольный запрос UID10005 во время VPN | HTTP `204`, его TCP tuple виден в обоих направлениях |
| Config/push | Loopback relay обслужил 4 config TLS и 3 push TLS соединения |
| Native TCP443 | 5 полных IPv4 tuples совпали с established-сокетами UID0; payload отмечен в обе стороны |
| Лимиты | 148 packet records, 40 726 bytes; 80 forwarded, 58 injected, 3 dropped, 7 служебных IPv6 control отброшены |
| Ошибки relay | Denied=0, IO failures=0, active handlers=0, unfinished uploads=0 после закрытия |
| Остановка | Собственный 10-секундный deadline; native join и stop подтверждены |
| Независимый откат | Watchdog действительно завершил процесс тестового пакета; наблюдение через 16,302 с от запуска |
| Восстановление | IPv4/IPv6 rules и настройки совпали с исходными; PID Agent/Voicebridge/adbd/audioserver сохранились |

[Сокращённый отчёт](../../experimental/vpn-relay/results/device-20221212.json)
содержит хеши проверенных сборок и границы результата. Полные packet payload,
учётные данные и журналы устройства не публикуются. Журнал содержит только
заголовки/длины и ограничен общим packet budget; записи выполняются перед
операцией передачи, поэтому одна строка журнала сама по себе не доказывает
доставку. Контрольный HTTP-ответ проверяется отдельно.

После сохранения результата тестовый APK, shell-копия, временные app_process
артефакты и журнал удалены. Автозапуска у них нет. OTA-guard остался `OK`,
Agent и веб-панель отвечают, локальные службы исправны. Рабочая схема
с выключенным Wi-Fi сохранена.

## Что изменилось относительно первого захвата

Первая [диагностическая проба](../../experimental/vpn-coverage/README.md)
только читала TUN и отбрасывала пакеты: контрольный HTTP-запрос тогда не мог
получить ответ. Теперь готов локальный TCP transport и проверена обратная
доставка. Перед включением настоящего TUN тот же native stack прошёл проверку
на Unix datagram socketpair без сетевого интерфейса.

При интеграции lwIP выдал собственный служебный IPv6 neighbor solicitation.
Сначала строгая проверка остановила пробу. Исправление лишь отдельно считает
и отбрасывает известные interface-up ICMPv6 control; они не попадают в TUN.
Остальной неожиданный IPv6 по-прежнему прерывает тест. Это не поддержка
IPv6-интернета. Для push увеличен Java idle timeout; абсолютный срок теста
и закрытие всех сокетов сохранены. Native idle timeout пока 3 секунды,
поэтому долговечность push-сессии этим проходом не подтверждается.
Финальный проход не дал IO failures.

## Границы результата

Некоторые соединения UID0 действительно проходят через наш VPN. Но UID0
включает несколько служб. Доступа к их `/proc/<pid>/fd` нет; принадлежность
именно `maind --updatesd` и URL `check_updates` этим захватом **не доказана**.
TLS ClientHello используется relay для локального SNI routing, а TLS payload
и URL не сохраняются. Счётчики config/push не устанавливают конкретный
native PID и не доказывают покрытие всех OTA-путей.

Привязка к physical Network уже проверена для системного UID Quasar и
обошла обычный VPN. Не проверены именно OTA-сокеты, существующие
keepalive, глобальный IPv6, поведение до запуска приложения, при его падении,
переподключении Wi-Fi и холодной загрузке. В Android 9 есть более приоритетные
правила privileged/protected sockets; успешный `/32` тест их не устраняет.
Источники: [AOSP RouteController](https://android.googlesource.com/platform/system/netd/+/refs/tags/android-9.0.0_r1/server/RouteController.cpp),
[FwmarkServer](https://android.googlesource.com/platform/system/netd/+/refs/tags/android-9.0.0_r1/server/FwmarkServer.cpp),
[официальное описание always-on](https://developer.android.com/develop/connectivity/vpn#always-on).

## Что нужно до включения домашнего Wi-Fi

1. Атрибутировать native config/OTA соединения и проверить обходы на
   изолированной сети для конкретных updater-путей и обеих IP-семей.
   Для системного Quasar уже получен отрицательный результат physical-bind
   контроля; добавление новых VPN-маршрутов само по себе его не устраняет.
2. Отдельно доказать системный запрет прямого выхода до готовности VPN,
   при сбое и после перезагрузки. Обычный force-stop может оставить
   системный lockdown и заблокировать ADB; его нельзя считать достаточным
   механизмом отката для таких испытаний.
3. Реализовать разрешённый внешний transport и убрать оставшиеся
   зависимости: ПК DNS/443/ADB relay, CONNECT:18443, время и запуск shell
   input helper после boot. Текущая `/32` проба доставляет только локальные
   службы; она не заменяет интернет-шлюз.
4. После этого испытать голос, свежую загрузку музыки, таймеры и пульт
   с отключённым ПК, включая холодную загрузку и аварийное завершение VPN.

## Почему простые альтернативы пока не подходят

- **Системный HTTP proxy:** native Quasar обходит его для config/OTA.
- **Подмена DNS:** не запрещает cached IP, прямой IP, иной DNS или IPv6.
- **Статический IPv4 с пустым шлюзом:** не закрывает независимый IPv6 RA/SLAAC.
- **Несохраняемый Wi-Fi:** AOSP9 умеет ephemeral config, но это hidden API;
  доступность и persistence vendor-прошивки не доказаны. Такая сеть сама
  по себе не отключается при падении фильтра.
- **Device Owner:** [проверка прав](android9-network-enforcement.md)
  показала отказ shell Binder getter из-за `CONTROL_VPN` и firewall getter
  из-за требования UID1000. Owner не назначался: он не закрывает системные
  обходы VPN и меняет другие настройки устройства.
- **Готовый Mali-root:** публичный
  [профиль](https://github.com/amirilivice/yandex-station-2-s905x2-root/tree/5b8db44ce55ecb68bd337fb45d5162c15ddae04b)
  проверен на `20220415`, а не нашем ядре. Найден boot-контейнер с датой
  `20221212`, но это `AMLSECU!`; открытый Image/символы для переноса не получены.
  Загрузчик показывает `locked`, verified boot — `green`, verity — `enforcing`.
  Временный root ещё не обеспечивает firewall до подключения сети.

Рабочее подключение по-прежнему использует изолированный Ethernet и
ограниченный транспорт ПК. Лабораторная доставка уже работает на Станции;
системная защита прямого интернет-выхода остаётся отдельной нерешённой задачей.
