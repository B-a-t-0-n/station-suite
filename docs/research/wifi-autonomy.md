# Автономный Wi-Fi на Макс: состояние исследования

Проверка 16 ноября 2026 года, Android 9, `PPR1.180610.011.20221212`.
Цель — домашний Wi-Fi без ПК и дополнительного роутера: служебные запросы
Станции остаются локальными, наружу разрешены только нужные API и медиа.
**Готового режима безопасного автономного Wi-Fi пока нет.**

Следующий этап проверил [права Android и варианты системного guard](android9-network-enforcement.md):
реальный shell Binder getter отказал из-за `CONTROL_VPN`, firewall getter —
из-за требования UID1000. Device Owner не назначался: он не закрывает
системные обходы VPN и имеет побочные эффекты. Отдельно разрабатывается
[локальный TCP/TLS transport](../../experimental/local-service-relay/README.md)
и закреплена сборка [native TCP stack под API28](../../experimental/native-tun2socks/README.md).
Эти компоненты не включены в основные приложения или автозапуск.

## Направление без root

Локальный `VpnService` остаётся проверяемым вариантом. Он должен доставлять
native config/OTA и push нашим локальным службам, а разрешённые внешние
соединения выпускать через узкую политику. Это не требует подписки на внешний
VPN. Общий системный HTTP proxy этой задачи не решает.

Сделана отдельная [диагностическая проба](../../experimental/vpn-coverage/README.md),
не включённая в основные приложения или автозапуск. Она на 10 секунд
перехватывает один IPv4 `/32` в изолированной проводной сети; Wi-Fi выключен.
DNS, default routes, always-on и lockdown не меняются. ADB UID2000, Agent и
Voicebridge исключены. Независимый shell-процесс завершает только тестовый
пакет через 15 секунд после аутентификации; без ARM максимальный срок — 30 секунд.

## Что действительно проверено

| Проверка | Результат |
| --- | --- |
| Независимый watchdog без VPN | Реальный PID MarkerService завершён; основные процессы продолжили работу |
| Связь приложения с watchdog | Loopback TCP, одноразовый challenge/HMAC; секрет не передаётся по TCP |
| Контрольный запрос UID10005 до VPN | HTTP `204` от нашей connectivity-заглушки |
| Тот же путь во время VPN | TCP-пакеты контрольного порта появились в TUN, ответа в срок не было |
| Наблюдение за 10 секунд | 20 IPv4-пакетов; 6 служебных IPv6-пакетов поднятия TUN отдельно учтены и отброшены |
| TCP:443 к тестовому config-адресу | Два захваченных TCP source-port совпали с `/proc/net/tcp`, UID0, `SYN_SENT`; TLS не декодировался |
| Завершение | Собственный deadline сработал; команда force-stop watchdog завершилась с кодом 0 |
| Восстановление | IPv4/IPv6 policy rules побайтно совпали с исходными; PID Agent/Voicebridge/adbd/audioserver сохранились |
| Конфигурация | Wi-Fi остался выключен, `http_proxy=null`, после проверки API сообщает `clockSize=middle` |

После сохранения результатов тестовый APK удалён. Его копии для shell и
контрольного app_process тоже удалены; автозапуска у них не было. Штатные
приложения, прошивка и настройки VPN always-on/lockdown не менялись.

APK проверенного прохода: SHA-256
`503d84699128cdb572fcf3a98e92e5a0e3e03b1344ea27edb999e702d31a4e5f`.
Исходники совпали с source hashes записи сборки. Финальные host-проверки:
85 assertions разбора/допуска, 289 классификатора IPv6 control и 77 HMAC,
включая независимые Python HMAC vectors. Это тесты диагностического кода,
не испытания полной сетевой защиты.

Первые два запуска прекращались сразу: reader не учитывал служебный IPv6
при поднятии TUN. После узкого исправления третий запуск продержался весь
интервал. Учитываются только ожидаемые ICMPv6 control; остальные неожиданные
пакеты по-прежнему прерывают эксперимент. Это не обработка IPv6-интернета.

## Границы результата

Получено прямое свидетельство, что некоторые соединения UID0 могут попадать
в наш VPN. Общее утверждение «root-процессы всегда обходят VpnService» неверно
для наблюдавшегося пути. Но UID0 включает несколько служб. Доступа к их
`/proc/<pid>/fd` нет; принадлежность именно `maind --updatesd` и URL
`check_updates` этими метаданными **не доказана**. Порт 443 сам по себе не
доказывает HTTPS; TLS-рукопожатие и содержимое запроса не анализировались.

Не проверены: все OTA-пути, physical-interface bind/protected sockets,
существующие keepalive, глобальный IPv6, поведение до запуска приложения,
при его падении, переподключении Wi-Fi и холодной загрузке. В Android 9 есть
более приоритетные правила privileged/protected sockets; успешный `/32`
тест их не устраняет. Источники:
[AOSP RouteController](https://android.googlesource.com/platform/system/netd/+/refs/tags/android-9.0.0_r1/server/RouteController.cpp),
[FwmarkServer](https://android.googlesource.com/platform/system/netd/+/refs/tags/android-9.0.0_r1/server/FwmarkServer.cpp),
[официальное описание always-on](https://developer.android.com/develop/connectivity/vpn#always-on).

## Что нужно до включения домашнего Wi-Fi

1. Атрибутировать отдельные native config/OTA соединения и проверить обходы
   на изолированной сети, включая явный physical bind и обе IP-семьи.
2. Реализовать локальную доставку TLS config/push и разрешённый transport.
   Нынешняя проба только отбрасывает пакеты, ничего не проксирует.
3. Отдельно доказать системный запрет прямого выхода до готовности VPN,
   при сбое и после перезагрузки. Android always-on/lockdown — предмет
   проверки на этой прошивке. Для таких тестов нужен механизм отката,
   который снимает и системный lockdown: обычный force-stop может оставить
   ADB заблокированным.
4. Убрать оставшиеся зависимости: ПК DNS/443/ADB relay, CONNECT:18443,
   время и запуск shell input helper после boot. Только затем испытать
   голос, свежую загрузку музыки, таймеры и пульт с отключённым ПК.

## Почему простые альтернативы пока не подходят

- **Подмена DNS:** не запрещает cached IP, прямой IP, иной DNS или IPv6.
- **Статический IPv4 с пустым шлюзом:** не закрывает независимый IPv6 RA/SLAAC.
- **Несохраняемый Wi-Fi:** AOSP9 умеет ephemeral config, но это hidden API,
  доступность и persistence vendor-прошивки не доказаны. Даже несохраняемая
  сеть не отключается автоматически при падении фильтра.
- **Готовый Mali-root:** публичный
  [профиль](https://github.com/amirilivice/yandex-station-2-s905x2-root/tree/5b8db44ce55ecb68bd337fb45d5162c15ddae04b)
  проверен на `20220415`, а не нашем ядре. Найден boot-контейнер с датой
  `20221212`, но это `AMLSECU!`; открытый Image/символы для переноса не получены.
  Загрузчик показывает `locked`, verified boot — `green`, verity — `enforcing`.
  Временный root ещё не обеспечивает постоянный firewall до подключения сети.

Рабочая схема остаётся прежней: изолированное Ethernet-подключение,
ограниченный транспорт ПК и выключенный Wi-Fi. Исследовательский результат
не меняет этот статус.
