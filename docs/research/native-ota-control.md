# Можно ли отключить native updater с текущими правами

Проверка 16 ноября 2026 года, Max / Android 9 / `20221212`. Выполнены только
чтение метаданных, проверка доступности записи и офлайн-анализ сохранённых
vendor-файлов. Сигналы остановки, IPC-команды, installer, root-бинарники и
перепрошивка не запускались. Wi-Fi и рабочие службы не менялись.

**Подтверждённый способ системного отключения OTA с текущими правами не найден.**
Это отдельная граница после уже обнаруженного [обхода VPN](vpn-system-bypass.md).
[Сокращённые результаты и хеши](results/native-control-20221212.json).

Повторная read-only проверка 17 ноября подтвердила shell UID2000/capabilities0,
отказ чтения обеих firewall-таблиц и отсутствие готового раннего hook.
Точные init и kernel config теперь прочитаны с устройства: ядро поддерживает
IPv4/IPv6 filtering, но `rc_local` запускается после netd/zygote и сам по себе
не задаёт барьер до сети. Добавлены [сборщик фактов и офлайн-проверка плана](../../experimental/egress-guard/README.md).
Они не устанавливают защиту и не разрешают включение Wi-Fi.

## Права на самой колонке

| Контекст | Фактические права |
| --- | --- |
| ADB shell | UID2000, effective Linux capabilities = 0 |
| `run-as` Quasar | UID10005, effective Linux capabilities = 0 |
| Native `maind --updatesd` | UID0, `CapEff=0000003fffffffff`, SELinux `quasar` |

Проверка сигнала **0**, которая только проверяет права, отказала обоим
доступным контекстам для updatesd. Настоящий stop/kill сигнал не отправлялся.
Наличие у Quasar привилегированного сетевого класса не означает наличие
Linux `CAP_KILL`, `CAP_NET_ADMIN` или прав на запись vendor-раздела.

У shell и Quasar недоступна запись в `launch.json`, `quasar-prod.cfg`,
`device_ota_update.sh`, `ota_script.pub`, supervisor и исполняемый `maind`.
Запись в cache/recovery-пути также не разрешена. `/cache` имеет владельца
`system:cache` и mode0770. Отказ доступа к вложенному пути не устанавливает
его наличие или отсутствие; файл recovery command и блочное устройство не открывались.

## Почему не найдено команды «выключить updatesd»

Проверен штатный диспетчер **`quasar_launcher2`**, не наш ТВ-лаунчер.
Его SHA256 указан в отчёте. Он однократно читает `nodes[0].tasks` из
vendor `launch.json` и поддерживает перезапуск дочерних процессов.

В исследованном исполняемом файле не найден интерфейс stop/remove/reload,
Unix-сокет или Binder control. Цикл использует `ppoll` с нулём descriptors;
зарегистрированный signal handler — `SIGCHLD`. Все четыре вызова generic
`syscall` разобраны как `gettid` и `sched_setaffinity`. Неизвестные поля
task отвергаются, поэтому добавление предполагаемого `enabled:false`
не является поддержанным способом. Копия конфига в `/data` сама не станет
активной. Остановка Android APK не останавливает этот root native child.

Сообщество удаляет конкретную задачу updatesd из защищённого launch-файла
с root и применяет изменение после загрузки. Это изменение конфигурации,
а не доступная обычному приложению команда supervisor.
[Пример сообщества](https://github.com/hu553in/yandex-station-root/blob/e5c3023762220b0d59b66eb651493b3c51d7c5c0/persistence.py).

## Почему cache chmod не заменяет защиту установщика

Штатный установщик размером 227 байт создаёт recovery directory, записывает
recovery command и затем безусловно запрашивает reboot в recovery.
Результат записи не проверяется; `set -e` нет. Поэтому даже предполагаемый
отказ записи не доказывает отсутствие перезагрузки. Скрипт не исполнялся.

У работающего updater есть root capabilities, а сохранённая политика SELinux явно
разрешает домену `quasar` запись в cache/recovery и `dac_override`. Обычное
изменение Unix mode папки не установлено как препятствие этому процессу.
Immutable — отдельный механизм с собственными правами/SELinux-проверками;
его возможность установки или снятия здесь не испытывалась.

В AliceBridge Max изменение cache permissions обозначено как дополнительная
защита, а build gate относится к `5000000921`. Station1 installer stub и
root freeze-watchdog относятся к другой платформе и не переносились.
[MaxSetup](https://github.com/Yandex-Station-Universal-Repo/AliceBridge_APP/blob/5b050393bad27c6cdb6ef68f24a3b8076e42cc59/station/src/main/java/dev/alicebridge/station/MaxSetup.java),
[MaxPlan](https://github.com/Yandex-Station-Universal-Repo/AliceBridge_APP/blob/5b050393bad27c6cdb6ef68f24a3b8076e42cc59/station/src/main/java/dev/alicebridge/station/MaxPlan.java).

## Уточнение старой истории root

Фраза «для этой сборки root никогда не было» была бы неверным обобщением.
В локальном архиве найдены доработанный baseline-бинарник, совпадающая копия,
восстановленные исходники и журнал с точной сборкой `20221212` и сообщением UID0.
Это сильнее, чем наличие только публичного профиля `20220415`.

Однако старый wrapper завершился `root_selinux_not_restored`, а не чистым
успехом: журнал заканчивается Permissive. Последующая диагностическая попытка
с другим бинарником сопровождалась потерей ADB и перезагрузкой, без
подтверждённых итоговых маркеров. Текстовые архивы не являются
криптографическим доказательством аппаратного прогона или текущего root.
Пригодность для безопасного повторения и автозапуска ими не доказана.
В этом этапе root-бинарники не собирались, не менялись и не запускались.

## Текущее решение

Рабочая пересылка на локальные config/push службы сохраняется. Но системный
запрет OTA, защита до старта приложений и автономная загрузка без ПК пока
не обеспечены. Для изменения protected installer/launch нужен отдельно
подтверждённый привилегированный канал, совместимость с загрузочной защитой,
резервная копия и проверенный откат. Рискованная замена файлов ради проверки
не выполнялась. Изолированная проводная схема и выключенный Wi-Fi сохранены.
