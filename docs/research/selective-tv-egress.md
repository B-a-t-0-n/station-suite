# Интернет для Android TV отдельно от штатной Алисы

Исследование 18 ноября 2026 года, Макс / Android 9 / `20221212`, домашний
RV6699. Исходная цель — оставить внешние службы штатной Алисы и OTA за
запретом, а установленным ТВ-приложениям дать интернет через отдельный
транспорт. Полная схема ещё не подтверждена. Позднее пользователь выбрал
обычный Wi-Fi-интернет с запретом известных IP Яндекса и принял отсутствие
гарантии блокировки OTA. Внешний туннель остаётся дополнительным направлением;
эта страница не сообщает результат текущей настройки обычного Wi-Fi.

## Что умеет текущий фильтр

Проверенный IP Filtering различает source/destination IPv4, маски,
TCP/UDP и порты. У ТВ-приложений и native-служб Станции один source IPv4;
эти правила не знают Android package, UID, процесс, имя TLS или HTTP path.
Поэтому проверенная закрытая политика с общим запретом ограничивает и Android TV.

Сохранённая форма RV6699 URL Filter содержит общий enable и максимум
16 доменов. В ней нет выбора source IP/MAC или отдельного устройства.
Help описывает совпадение домена с поддоменами, но форма не доказывает
реальную фильтрацию HTTPS/SNI, QUIC, DoH, кешированных адресов или прямого
IP. Глобальная настройка не включалась: она может затронуть остальные
устройства дома, не решив задачу этой Станции.

## Почему одного списка доменов пока недостаточно

Точный сохранённый `quasar-prod.cfg` имеет SHA-256
`685c4b8cdfbef945ff90c4dff932dbbfd34cc4db2d5eee3fd21aefd5f2a2af5b`.
В нём найдены следующие направления; это конфигурационный список,
а не полная трасса соединений или готовый список блокировки OTA.

| Назначение | Имена из конфигурации |
| --- | --- |
| Config/backend | `quasar.yandex.net`, `quasar.yandex.ru` |
| Штатный голос | `uniproxy.alice.yandex.net` |
| Авторизация | `oauth.yandex.ru`, `mobileproxy.passport.yandex.net`, `passport.yandex.ru` |
| Push | `push.yandex.ru` |
| Музыка | `ws-api.music.yandex.net` |
| IoT и геолокация | `iot.quasar.yandex.ru`, `api.lbs.yandex.net` |
| Проверка связи и HTTP time fallback | `scbh.yandex.net` |
| Телеметрия | `startup.mobile.yandex.net`, `clck.yandex.net` |
| Заставки и общие ресурсы | `quasar.s3.yandex.net`, `yastatic.net` |
| Native NTP | `0.ru.pool.ntp.org` — `3.ru.pool.ntp.org` |

Локальный push Suite дополнительно использует
`station-config.quasar.yandex.net`. В исследованном разделе updatesd нет
отдельного фиксированного домена архива OTA. Нельзя считать блокировку
одного предполагаемого download-адреса покрытием всех обновлений.

DNS-ответы меняются, IP могут принадлежать общим CDN. Широкая блокировка
сетей Яндекса может задеть логины и ресурсы ТВ-приложений. Подмена DNS
не закрывает прямой IP, другой resolver, IPv6 и уже доказанный
[выбор физической сети системным Quasar вне VPN](vpn-system-bypass.md).

## Проверяемый вариант с отдельным туннелем для ТВ

Дополнительный вариант — сохранить source IPv4 default deny на роутере
и разрешить только точные IP/порт/transport внешнего VPN-сервера.
Выбранные ТВ-пакеты направлять через туннель на самой Станции. Тогда
разные внешние адреса Android TV доступны внутри этого соединения,
а обычные прямые запросы native-служб остаются за роутерным запретом.
Это проектируемая схема, не результат аппаратной проверки.

Нужны работающий внешний endpoint и подтверждённый режим включения
конкретных приложений в туннель. Установка Happ не доказывает наличие
подходящего профиля. Целые сети VPN-провайдера или произвольные разрешения
TCP/443 вместо точного endpoint не предполагаются. Роутер всё равно
не различает процессы; это не защита от злонамеренного root.

Есть существенная интеграционная задача: у одного пользователя Android
может быть только один активный VpnService; старт другого останавливает
предыдущий. Happ и текущий split VPN Suite нельзя считать одновременно
работающими. Локальную доставку config/push/DNS придётся объединить с
общим транспортом либо отдельно доказать другой путь.
[Официальная документация Android](https://developer.android.com/develop/connectivity/vpn#service).

### Что подтверждено в установленном Happ

В APK Happ `4.10.1` / versionCode `1731` (SHA-256
`169f39f9d79ab4d6343588c3ed107e9113f1ecaf793e9ecd06a4fe7e6cc6e7b5`)
проверены manifest, ресурсы и соответствующие участки DEX. Класс
`su.happ.proxyutility.service.HappProxyOnlyService` наследуется от обычного
`android.app.Service`, отдельно от `HappVpnService`. Он запускает ядро
по выбранному профилю и сам не создаёт Android TUN. Proxy-only — реальный
путь реализации, но его работа на этой Станции пока не проверена.

У Happ также реализованы списки приложений: ON вызывает
`VpnService.Builder.addAllowedApplication`, BYPASS —
`addDisallowedApplication`. Важная особенность: **ON с пустым или
отсутствующим списком включает в VPN все приложения, кроме самого Happ**.
Поэтому для пробы только с ТВ нужен проверенный непустой список конкретных
пакетов. Текущие профили и настройки приложений при этом аудите не читались.

Возможная схема `Suite VpnService → локальный SOCKS → Happ Proxy-only`
обошла бы конфликт одного активного VpnService, но пока остаётся гипотезой.
Нужно подтвердить локальный SOCKS, маршрутизацию его исходящих соединений,
совместную работу и разделение ТВ/native-трафика. Текущий split VPN Suite
перехватывает локальные config/DNS-направления, а не предоставляет готовый
общий транспорт для ТВ. Простая пересылка всего трафика в Happ могла бы
открыть тот же путь штатным службам и OTA. Устройства и сеть в ходе
APK-аудита не изменялись.

### Владелец соединения: результат на Станции

В текущем relay есть адрес назначения, но нет готового признака Android
package/UID. Если добавить пересылку всех внешних соединений в Happ, доступ
могут получить и захваченные штатные службы. Поэтому отдельно проверена
видимость владельцев сокетов из обычного UID нашего Wi-Fi-приложения.

Короткая проба выполнялась при выключенных Wi-Fi и VPN. Реальный процесс
APK с UID10040 открыл только `127.0.0.1:24111`; диагностический клиент под
Quasar UID10005 подключился с `127.0.0.1:24110`, без передачи payload.
Приложение прочитало `/proc/net/tcp` и `/proc/net/tcp6`, нашло обе стороны
ESTABLISHED-соединения и правильно различило UID10005 и UID10040. В результат
попали только эти две пары; остальные соединения не сохранялись. Сокеты
закрылись, временный DEX и файл результата удалены, Wi-Fi/VPN остались выключены.
[Сокращённый отчёт](results/socket-owner-loopback-2026-11-18.json).

Следующая ограниченная проба подтвердила и **новый SYN непосредственно из TUN**.
Диагностический VpnService установил только маршрут `198.18.0.254/32`, без
default route и DNS. Клиент под UID10005 сделал обычный TCP connect, без
привязки к физической сети и без защиты сокета от VPN. APK под собственным
UID10040 поймал один SYN и нашёл его точный tuple в `/proc/net/tcp{6}` в состоянии
`SYN_SENT` (`02`): владелец UID10005, однозначно и не собственный UID приложения.
Пакеты не пересылались, handshake и передача payload не выполнялись; ожидаемый
отказ connect не является ошибкой этой пробы. TUN закрылся, независимый guard
завершился до очистки, Wi-Fi/VPN остались выключены. PID Agent и Voicebridge
сохранились, их heartbeat продолжился.
[Сокращённый результат SYN-пробы](results/socket-owner-syn-2026-11-18.json).

Это подтверждает видимость владельца одного нового соединения на нашей Android 9,
но не готовый контроль ТВ-трафика. Переполнение/гонки таблиц, повторное использование
tuple, нагрузка и передача полного потока через внешний backend ещё не доказаны.
Для будущего admission отсутствие полной однозначной записи должно означать отказ.
Публичный `getConnectionOwnerUid` появился только в API29; полагаться на него
на API28 нельзя.
[Документация Android](https://developer.android.com/reference/android/net/ConnectivityManager#getConnectionOwnerUid(int,%20java.net.InetSocketAddress,%20java.net.InetSocketAddress)).

Есть дополнительная граница: нынешний loopback SOCKS relay не требует
аутентификации и безопасен для своей узкой задачи потому, что отдаёт только
локальные backends. Добавлять туда общий WAN fallback без отдельного
контролируемого входа нельзя: локальный CONNECT обошёл бы проверку пакета
на входе TUN. Доступ к Happ inbound также нужно проверить и ограничить.
Полная изоляция от злонамеренного root этой схемой не заявляется.

Ограниченная будущая проба должна подтвердить одновременно:

1. HTTPS с нормальной проверкой сертификата из ТВ-контекста проходит через
   разрешённый endpoint.
2. Контрольное соединение системного Quasar с выбором физического Wi-Fi
   не получает прямой внешний доступ; локальные службы доступны.
3. Управление остаётся доступным, падение туннеля не снимает router deny,
   собственное разрешение удаляется независимым восстановлением.

Выбранный пользователем режим с запретом известных IP — отдельный компромисс:
он допускает обычный интернет, но не закрывает новые адреса, общие CDN,
альтернативные DNS и возможные обходы. Результаты SYN-пробы не превращают его
в гарантированную защиту от OTA и не требуют внешнего VPN для его использования.
