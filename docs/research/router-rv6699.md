# RV6699: проверка фильтрации для Станции

17 ноября 2026 года. Проверен домашний Sercomm RV6699 с прошивкой
`v4.4.59`. Доступ к веб-панели получен стандартной учётной записью;
массовый перебор не проводился. Версия на наклейке отличается от текущей.

**Исходящая IPv4-фильтрация после глобального Apply подтверждена.**
Узкое правило для тестового телефона заблокировало два новых TCP/443
соединения; контрольный адрес продолжал отвечать. Отдельно проверены
UDP/53 и разрешение из первой группы перед запретом из второй.
Защита самой Станции от OTA ещё не настроена.

## Уточнение после проверки штатного интерфейса

В сохранённом `template.js` функция `applyAP()` отправляет отдельную форму:

```text
todo=apply
this_file=global_nav.htm
next_file=<текущая страница>
```

Прежние скрипты выполняли сохранение через `todo=save`, но не этот шаг.
В сохранённой странице редактора оставалось сообщение
`Please do Apply to make the changes take effect.` Поэтому прежний вывод
об отсутствии рабочей фильтрации был преждевременным: таблица ниже
описывает соединения при сохранённых, но не подтверждённых как применённые
правилах. Выбранный в панели режим Custom также не доказывает его применение.

## Повторная проверка с глобальным Apply

Проверено одно правило IP Filtering: интерфейс HSI, цепочка Output
(`ouput` в штатной форме), Forward выключен, IPv4 источника и назначения
с маской `/32`, TCP, порт назначения 443. Глобальный режим firewall
оставался Medium; Custom для этой проверки не потребовался.

| Этап | Запрещаемый адрес | Контрольный адрес |
| --- | --- | --- |
| До изменения | HTTPS 301 | HTTPS 301 |
| После Save, до Apply | HTTPS 301; в панели запрос Apply | Проверен на исходном этапе |
| После глобального Apply | Два новых соединения не установились (`ConnectException`) | HTTPS 301 |
| После удаления и глобального Apply | HTTPS снова доступен | HTTPS снова доступен |

Сообщение о необходимости Apply исчезло после применения. Админка
оставалась доступна во время запрета. Независимый watchdog удалил свою
группу, отправил Apply и проверил восстановление связи. Сохранённые
параметры Advanced Firewall совпали с исходными; таблицы IP Filtering
и black/white list пусты, ожидающих Apply изменений нет.

Телефон использовался также для временного USB/Wi-Fi транспорта к фиксированному
адресу админки: маршрут ПК в этот момент уходил через VPN. Это не требовало
изменения маршрутов ПК или настроек телефона. Временные DEX, процесс и
собственный ADB forward после проверки удалены.

## Порядок групп и UDP

Следующая проба ограничивалась тем же одним телефоном и одним внешним
адресом. В первой группе разрешался TCP/443, во второй запрещались
TCP/UDP на всех портах к этому адресу. Обе группы привязаны к HSI/Output;
режим Medium не менялся. После каждого изменения выполнялся глобальный Apply.

| Применённые группы | TCP/443 к целевому адресу | UDP DNS к нему | Контрольный адрес |
| --- | --- | --- | --- |
| Allow TCP/443, затем deny TCP/UDP | HTTPS 301, сертификат проверен | Нет валидного ответа | HTTPS и UDP DNS доступны |
| Только deny TCP/UDP | Новое соединение не установилось | Нет валидного ответа | HTTPS и UDP DNS доступны |
| После удаления обеих групп | Доступ восстановлен | Ответ DNS восстановлен | Оба протокола доступны |

Это подтверждает порядок разрешения/запрета в проверенной конфигурации
и действие запрета на UDP. Общий запрет всех внешних назначений, ранее
установленные соединения и сохранение политики после reboot ещё не проверены.
Откат подтвердил исходные группы и Advanced Firewall, отсутствие ожидающего
Apply и восстановление всех четырёх проб.

DNS-снимок через домашний Wi-Fi разрешил все 38 точных имён нашего
транспорта: 47 IPv4, либо 42 CIDR без добавления посторонних адресов.
Минимальный TTL в снимке — 8 секунд. Несколько групп снимают ограничение
одной группы из 32 правил, но статический снимок быстро устаревает.
Автоматическое обновление списка не реализовано; IP-фильтр не различает
TLS-имя или процесс на Станции. Широкие сети провайдеров не разрешались.

## IPv6 только для Станции

Общее отключение IPv6 в домашней LAN пользователь отклонил; настройка
сохранена включённой. На тестовом телефоне сейчас только link-local IPv6,
что не доказывает отсутствие IPv6-выхода в будущем.

В штатном интерфейсе найдены гостевые SSID, Block Guest Wireless Bridging,
LAN MAC Control и четыре контекста LAN. Настоящий Subnet2 открыт штатным
`todo=update_lan`, подтверждён `h_subnet_select=1`, затем возвращён контекст 0.
Основные поля совпали с исходными, ожидающего Apply нет. Настройки сети
не сохранялись. Наличие IPv6-полей в Subnet2 не устанавливает независимое
управление IPv6; Conditional Serving выбирает DHCP-пул, но не доказывает
изоляцию IPv6 RA. Отдельного IPv6/EtherType-фильтра по MAC в просмотренных
формах нет. Гостевая сеть как готовое решение пока не подтверждена.

На самой Станции подтверждены `CONNECTIVITY_INTERNAL` у ADB shell UID2000
и типизированные методы `INetworkManagementService.enableIpv6/disableIpv6`.
При выключенном Wi-Fi выполнен короткий round trip только для `wlan0`:
исходный `disable_ipv6=1` → `0` после enable → `1` после disable. Отдельный
процесс повторно восстановил `1`. Wi-Fi не включался; исходные Wi-Fi,
proxy, SELinux и обе таблицы IP rules совпали после проверки. Временный
JAR удалён. Root и настройки роутера для этой пробы не использовались.

**Это работающий временный рычаг управления интерфейсом, не готовый
автономный барьер.** AOSP9 IpClient повторно включает IPv6 при provisioning.
Ранний сохраняемый запрет до первой сети, reconnect и холодная загрузка
ещё не доказаны. Подробнее — [аудит Android](android9-network-enforcement.md#ipv6-отдельного-интерфейса).

## Условия проверки

До изменения настроек скачана исходная резервная копия конфигурации.
Пароли, резервная копия, адреса домашних устройств и сырые страницы
хранятся приватно, вне репозитория.

Временные правила ограничивались одним тестовым телефоном, одним внешним
IPv4-адресом, TCP-портом 80 либо 443 и позднее UDP/53. Станция оставалась в изолированной
проводной сети с выключенным Wi-Fi. Для удаления каждого временного
набора запускался отдельный процесс с ограниченным сроком работы.

Каждая проба создавала новый сокет, явно привязанный к Android Wi-Fi Network,
и сверяла его локальный IPv4 с адресом телефона. Поэтому прохождение
через мобильную сеть не объясняет результат. В HTTPS-пробах проверялись
цепочка сертификата и имя узла. Контрольный адрес использовался отдельно
от адреса, который требовалось заблокировать.

## Прежние результаты без глобального Apply

| Настройка | Проверка сохранения | Сетевой результат |
| --- | --- | --- |
| Black list: MAC, IPv4 источника и назначения, TCP 80 | Правило сохранено и включено | Запрещаемый адрес ответил HTTP 301 |
| IP Filtering, LAN: input и output в отдельных проходах | Группа сохранена | Адрес ответил HTTP 301 |
| IP Filtering, HSI: output | Группа сохранена | Адрес ответил HTTP 301 |
| Одиночный drop без дополнительного allow, LAN/HSI | Drop прочитан из сохранённой группы | HTTP и HTTPS прошли |
| Firewall Custom: LAN и HSI одновременно, input и output, TCP 443 | Custom, обе цепочки и сохранённый drop подтверждены | HTTPS прошёл с проверкой сертификата |

В интерфейсе и обработчике прошивки токен output записан как `ouput`;
при сохранении использовалось именно штатное написание. Успешные
проверки после удаления правил подтвердили доступность обоих адресов.

Повторная проверка подтвердила действие Apply для IP Filtering. Прежние
пробы без этого шага не устанавливают работоспособность остальных режимов.
Оснований объяснять их результат неисправностью фильтра или аппаратным
ускорением нет.
Общий white list, Firewall High и
Block Whole Internet Communication не применялись: их влияние только
на одну Станцию не установлено. Работа фильтров с IPv6 и OTA-адресами
не подтверждена.

## Восстановление и итоговое состояние

После возврата из Custom в Medium прошивка изменила один дополнительный
параметр ICMP. Для восстановления загружена исходная резервная копия
через штатную форму роутера; роутер перезапустился.

После загрузки проверено:

- Все сохранённые до тестов скрытые параметры Advanced Firewall совпали
  с исходными, включая ICMP; режим снова Medium.
- Таблицы групп IP Filtering и black/white list пусты.
- Новые HTTPS-соединения телефона через Wi-Fi к обоим контрольным адресам
  проходят с проверкой сертификата.
- Wi-Fi Станции выключен. Проводной транспорт имеет состояние `ready`,
  локальные службы — `healthy`, панель отвечает HTTP 200.

Теперь подтверждены IPv4/TCP и UDP запреты для одного источника/назначения
и порядок Allow перед Deny в двух группах.
Готовой политики для защищённого Wi-Fi Станции этот этап ещё не дал.
Перед её включением нужны разрешённые направления и запрет остальных,
проверки полной политики, IPv6, сохранения после перезагрузки роутера,
новых и уже установленных соединений. По ограниченным пробам нельзя утверждать
полное перекрытие OTA.
Рабочая схема остаётся проводной с ограниченным транспортом ПК.
Общие границы исследования описаны в [состоянии автономного Wi-Fi](wifi-autonomy.md).
[Результаты без данных домашней сети](results/router-rv6699-2026-11-17.json)
сохраняют сетевые ответы и итоговую проверку восстановления.
