# Зависание Станции: диагностика 17 ноября 2026 года

Пользователь сообщил о повторных полных зависаниях: не работают ТВ-режим
и кнопка Алисы, проводное управление недоступно, после перезапуска работа
возвращается. Доступный снимок снят уже после перезагрузки, поэтому причину
предыдущего зависания он не устанавливает.

## Что подтверждено

- В Windows пропадал физический Ethernet link к Станции. По одному этому
  признаку нельзя отличить проблему кабеля от остановки сетевой части устройства.
- Задача `StationLab-KeepAlive` на ПК оставалась в одном запуске с 15:16.
  Политика `IgnoreNew` не позволяла минутным проверкам повторяться, поэтому
  автоматическое восстановление проводного транспорта не происходило.
- После перезагрузки Android сначала показывал дату сборки 2022 года.
  После восстановления проводных служб время синхронизировалось;
  пользователь подтвердил появление обычных часов на дисплее колонки.
- В снимке после загрузки доступно около 1,1 ГБ RAM, swap не используется,
  `/data` занято примерно на 9%. Доступный logcat не содержит OOM, ANR,
  fatal exception/signal или срабатывания системного Watchdog. Это
  характеризует только новый запуск и не исключает такие события до reboot.
- После неуспешной проверки Ethernet штатный Quasar сам включал Wi-Fi.
  Затем в журнале повторялись ошибки Wi-Fi HAL. Подготовленный тестовый
  профиль был отключён; адресов Wi-Fi в снимке нет. Ошибки HAL остаются
  наблюдаемым признаком, а не доказанной причиной зависания.
- Чтение журналов прошлого запуска, kernel/pstore и tombstones через
  имеющийся shell недоступно. Сохранённые Dropbox записи относятся к
  загрузке и не показывают причину предыдущего полного зависания.

## Исправление и текущее состояние

Проверка планировщика теперь вызывает [keepalive.py](../../pc/keepalive.py):
на один `start.py --ensure` отведено 25 секунд. По таймауту завершается только
непосредственный проверяющий процесс. Независимый runtime owner продолжает
работать; это проверено отдельным дочерним процессом в тесте. Вывод проверки
не ждёт закрытия унаследованных pipe handles и при ошибке не раскрывает
сырые stdout/stderr.

Старый зависший запуск задачи остановлен, проводной owner восстановлен.
Повторные запуски `StationLab-KeepAlive` завершились с результатом 0,
runtime и туннель имеют состояние `ready`, Agent отвечает HTTP 200.
Wi-Fi выключен. Изменения root/init/firewall на Станции для этой диагностики
не выполнялись. Исправление задачи устраняет найденный сбой восстановления
на ПК; оно не доказывает устранение полного зависания Android.

## Запись следующего сбоя

[Watch-StationHealth.py](../../tools/Watch-StationHealth.py) сохраняет
read-only диагностику в личный каталог вне Git. Каждые 30 секунд записываются
физический link Windows при наличии `psutil`, доступность ADB и Agent,
uptime, RAM/swap, счётчики CPU, Wi-Fi, разница времени и состояния PC runtime
и туннеля. Опционально ведётся непрерывный logcat с временем приёма на ПК:
это позволяет сопоставлять события даже после смены часов Android.

По умолчанию запись завершается через четыре часа; файл `stop` в каталоге
вывода позволяет закончить раньше, при следующей проверке. Health-журнал
ограничен четырьмя файлами по 1 МиБ, logcat — тремя по 4 МиБ. Recorder не
включает сеть, не перезапускает службы и не восстанавливает ADB самостоятельно.
При завершении останавливается только его собственный logcat-клиент.
Сырые журналы могут содержать личные данные и не предназначены для GitHub.

Пока запись не захватила повторный сбой, точная причина остаётся неизвестной.
Новые сетевые эксперименты не являются частью этой диагностики.
