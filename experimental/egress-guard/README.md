# Ранний сетевой барьер: офлайн-проверка плана

`guard_plan.py` проверяет форму входных наблюдений и показывает, что мешает
реализовать ранний запрет внешнего выхода native Quasar/updater на Max
Android 9 / `20221212`. Он не соединяется со Станцией, не вызывает ADB,
root, subprocess или сетевые команды, не создаёт правила и не меняет файлы.

Это подготовка к отдельному привилегированному эксперименту. Работающего
барьера здесь ещё нет. [Почему обычного VPN недостаточно](../../docs/research/vpn-system-bypass.md).

## Запуск

Из корня репозитория:

Сначала `probe_device.py` может собрать ограниченный read-only снимок нашей
точной прошивки через уже работающий ADB. Он не устанавливает APK, не
подключает Wi-Fi, не вызывает root и не меняет правила. В снимок не входят
серийный номер, MAC, аккаунты, ключи и содержимое трафика. Совпадение boot ID
проверяется до и после сбора, чтобы не объединить сведения разных загрузок.
Ошибка выдаёт только фиксированный код; raw-вывод ADB не печатается.

```powershell
python experimental/egress-guard/probe_device.py --adb C:/Android/platform-tools/adb.exe --target 192.168.77.100:5555 > C:/StationPrivate/guard-observations.json
```

`C:/StationPrivate` должен существовать. При ошибке сбора не передавайте его
вывод в оценку плана. TCP ADB признаётся `wired_ip` только при совпадении
адреса с `eth0`; это не доказательство независимого канала восстановления.
USB-серийный номер сам по себе такого доказательства также не даёт.

```console
python experimental/egress-guard/guard_plan.py --observations experimental/egress-guard/observations.example.json --policy experimental/egress-guard/policy.example.json
python -m unittest discover -s experimental/egress-guard/tests -p "test_*.py" -v
```

Пример наблюдений описывает непривилегированный shell. Значения нужно брать
из отдельно собранного read-only снимка, а не подменять ради зелёного ответа.
UID API-брокера `10046` в примере — только образец: после переустановки его
нужно заново сверить с действительным пакетом/подписью. Защищаемые UID0 и
Quasar UID10005 относятся к исследованной прошивке; это не универсальный профиль.

JSON имеет строгую схему: лишние поля, включая `otaProtected`, `applyCommand`
или булевы заявления о проверенном boot/recovery, отвергаются. Присутствие
`iptables`/`ip6tables` означает лишь наличие исполняемых файлов; поддержку
ядром и разрешение SELinux оно не доказывает. Тип `wired_ip` не считается
независимым физическим каналом восстановления.

Выход `1` означает оценённый, но не подтверждённый план; `2` — ошибку входа.
Успешного кода готовности нет. Даже JSON с UID0/CAP_NET_ADMIN/обоими бинарниками
получает `runtimeProtection:unverified`, `wifiMayBeEnabled:false` и список
непроверенных условий. Сам файл наблюдений не является доказательством работы
на устройстве. Пароли, ключи, адреса аккаунтов и raw-трафик не нужны.

## Минимальная будущая архитектура

План содержит четыре этапа, а не текущие состояния устройства:

1. **SEALED.** До доступного WAN у обеих IP-семей действует запрет. Независимый
   канал восстановления проверен на изолированном стенде; штатный updater
   не получает внешнего маршрута раньше guard.
2. **LOCAL_READY.** Локальные config/voice/music/DNS/time службы измерены,
   identity/UID пакетов сверены. Native UID сохраняют запрет прямого WAN.
3. **GUARDED.** Под Enforcing реально проверены IPv4/IPv6, прямой IP,
   сохранённый DNS, привязка к физическому Network и уже открытые соединения.
   Общий `ESTABLISHED` не должен разрешать native WAN раньше запрета.
   Собственная политика сохраняется при падении helper и изменениях netd.
4. **WIFI_ALLOWED.** Ранняя загрузка и свежий барьер готовности подтверждены
   отдельно на canary-сети. Разрешённый внешний доступ получает контролируемый
   API/TV-контекст, native продолжает обращаться к локальным службам.

Будущий helper должен иметь UID0, effective `CAP_NET_ADMIN`, подходящий SELinux
домен и проверенную поддержку обеих семей. Этого недостаточно для persistence:
нужен совместимый с AVB способ запуска до открытия сети и доказанный барьер
готовности. Обычный Android `BOOT_COMPLETED`, порядок асинхронных `start`,
временный root и сохранённый preference такие свойства не устанавливают.

Фильтр должен владеть отдельной политикой, сохранять правила Android/netd,
разрешать узкий путь управления и оставаться закрытым при падении helper.
Удалять запрет в обработчике выхода нельзя. Обе семьи настраиваются, пока
внешний интерфейс недоступен; затем проверяется фактическая политика.
Периодическое восстановление удалённого netd правила само по себе оставляет
промежуток и не считается непрерывной защитой.

Сетевой запрет не предназначен для противодействия злонамеренному root,
который сам может переписать firewall. Задача — исключить штатные внешние
запросы native-служб при обычной загрузке и сбоях нашей модификации.

## Что ещё требует аппаратной проверки

- Разрешение SELinux на netfilter, kernel extensions и фактическая установка
  правил; наличие бинарника или capability не заменяет canary.
- Точная vendor boot-цепочка и AVB, холодный старт с новыми rules до Wi-Fi.
- Сохранение guard при netd/переподключении/падении и поздних native стартах.
- Отрицательные запросы UID0/Quasar и положительные API/локальные запросы.
- Восстановление через действительно независимый канал, а не тот же IP-стек.

Пока эти условия не измерены, этот компонент не даёт разрешения включать
прямой Wi-Fi и не утверждает блокировку OTA. [Границы текущих прав](../../docs/research/native-ota-control.md).

## Проверка 17 ноября 2026 года

С живой Станции получен снимок: UID2000, effective capabilities `0`, SELinux
Enforcing, Android 9/build `20221212`; оба firewall-бинарника присутствуют.
Чтение `iptables -S OUTPUT` и `ip6tables -S OUTPUT` отдельно получило отказ
доступа. План правильно возвращает `PRIVILEGED_PRINCIPAL_MISSING` и
`CAP_NET_ADMIN_MISSING`. [Сокращённый результат](results/device-preflight-20221212.json).

С устройства прочитаны точные `/init.rc` и три `init.amlogic*.rc`, а также
`/proc/config.gz`. В ядре включены IPv4/IPv6 filter и conntrack, Android
qtaguid; фактическая установка правил не проверена. По live init `netd` и
zygote запускаются раньше `class_start main`; `rc_local` — root service этого
класса, без проверенного барьера готовности для Wi-Fi. Добавление команды
в поздний `rc_local` не закрывает загрузочный промежуток.

Доступные контексты не смогли прочитать protected `rc_local.sh`/`onboot.sh`;
проверенного writable hook не найдено. Ранняя привилегированная интеграция
остаётся блокером. Этот этап не устанавливает firewall, не включает Wi-Fi,
не исполняет kernel exploit и не изменяет init/vendor/SELinux.
